** cortexM 字节对齐规则
#+begin_example
    Cortex-M 系列的字节对齐规则基于 ARM 架构的内存访问机制，对齐要求旨在提高内存访问效率，并避免因未对齐访问而引发硬件故障
#+end_example
*** 字节对齐的基本原则
#+begin_src c
    对齐要求：
        数据类型的地址必须是其大小的倍数：
            uint8_t 或 char（1 字节）：可以存储在任何地址。
            uint16_t 或 short（2 字节）：地址必须是 2 的倍数（最低 1 位为 0）。
            uint32_t 或 int（4 字节）：地址必须是 4 的倍数（最低 2 位为 0）。
            uint64_t 或 double（8 字节）：地址必须是 8 的倍数（最低 3 位为 0）。
    
    未对齐访问定义： 数据的地址不满足上述对齐要求（例如，uint16_t 存储在奇数地址），则称未对齐访问（Unaligned Access）。
#+end_src
*** Cortex-M 未对齐访问的处理
#+begin_example
      默认行为：
          Cortex-M0 和 Cortex-M1：不支持未对齐访问，尝试未对齐访问会触发 HardFault
          Cortex-M3、Cortex-M4、Cortex-M7：默认支持未对齐访问，但未对齐访问性能会显著降低
    
      性能影响：
          未对齐访问通常需要多次内存读取和数据合并，因此性能较低
          对于性能敏感的系统（如实时系统），应尽量避免未对齐访问
    
      配置控制：
          Cortex-M3、M4 和 M7 的 SCB_CCR 寄存器中的 UNALIGN_TRP 位可以控制未对齐访问：
              设置为 1：触发硬件故障
              设置为 0（默认）：允许未对齐访问
#+end_example
*** 字节对齐的实际应用
#+begin_example
      变量对齐： 编译器通常会自动对变量进行对齐，例如
      struct example {
          uint8_t a;    // 1 字节
          uint16_t b;   // 2 字节
      };
      在默认情况下，b 的地址会对齐到 2 的倍数，结构体的大小可能会填充到满足更高对齐要求。
      手动对齐：
          在某些情况下可以通过编译器指令指定对齐方式，例如：
          uint32_t data __attribute__((aligned(4))); // 强制对齐到 4 字节
      未对齐访问的手动处理： 如果必须访问未对齐的数据，可以通过逐字节操作来避免异常：
    
          uint8_t *ptr = (uint8_t *)0x200046c1;
          uint16_t value = ptr[0] | (ptr[1] << 8); // 手动拼接
    
           一些外设（如 DMA 控制器）要求内存地址对齐到特定的边界（如 4 或 8 字节）。在使用外设时需特别注意地址对齐。
#+end_example


* 访问结构体成员， 可能该成员地址非对齐访问？
#+begin_example
这是一个非常关键且实际的问题。答案是：是的，访问结构体成员确实可能导致非对齐访问，但这取决于多个因素。

核心情况分析
1. 默认情况：编译器会保证对齐
在大多数情况下，编译器会自动插入填充（padding）来确保每个成员都自然对齐，除非你明确要求不这样做。

c
struct Example1 {
    uint8_t  a;      // 地址：0x00
    // 编译器自动插入3字节填充（假设从0开始）
    uint32_t b;      // 地址：0x04 (4字节对齐✓)
    uint16_t c;      // 地址：0x08 (2字节对齐✓)
    // 可能再插入2字节填充，使结构体大小为12字节（4的倍数）
};
在这种情况下，访问 b 和 c 都是对齐的。

2. 导致非对齐访问的常见场景
场景1：使用 packed 属性（最危险）
当你使用 __packed、__attribute__((packed)) 或 #pragma pack(1) 时，编译器会移除所有填充。

c
// 使用GCC/Clang的packed属性
struct __attribute__((packed)) SensorData {
    uint8_t  header;   // 地址：0x00
    uint32_t value;    // 地址：0x01 ← 非4字节对齐！⚠️
    uint16_t checksum; // 地址：0x05 ← 非2字节对齐！⚠️
};
// 总大小 = 7字节

// 访问成员可能产生非对齐访问
SensorData data;
uint32_t val = data.value; // 可能触发硬件异常或性能损失
场景2：强制类型转换或指针运算
c
struct NormalStruct {
    uint8_t a;
    uint32_t b;  // 编译器会填充，b在偏移4处
};

uint8_t buffer[10];
struct NormalStruct* s = (struct NormalStruct*)&buffer[1]; 
// 危险！结构体起始地址为0x01（不是4的倍数）
// 即使结构体内部有填充，整个结构体地址也不对齐

uint32_t val = s->b;  // 双重不对齐！可能崩溃
场景3：通过指针访问中间数据
c
#pragma pack(1)
struct Packet {
    uint8_t  id;
    uint32_t data;  // 偏移1，非对齐
};
#pragma pack()

void process_packet(uint8_t* raw_data) {
    struct Packet* pkt = (struct Packet*)raw_data;
    uint32_t value = pkt->data;  // 非对齐访问！
    
    // 更安全的做法：使用memcpy
    uint32_t value_safe;
    memcpy(&value_safe, &raw_data[1], sizeof(uint32_t));
    // 或使用编译器内置的非对齐访问函数
}

1. 编译时检查
c
// 使用static_assert检查结构体对齐
#include <stddef.h>
#include <assert.h>

struct GoodStruct {
    uint8_t a;
    uint32_t b;
    uint16_t c;
};

// 检查偏移量是否对齐
static_assert(offsetof(struct GoodStruct, b) % 4 == 0, 
              "b is not 4-byte aligned!");
static_assert(offsetof(struct GoodStruct, c) % 2 == 0,
              "c is not 2-byte aligned!");
static_assert(sizeof(struct GoodStruct) % 4 == 0,
              "Struct size not multiple of 4!");
2. 运行时检测（针对指针）
c
// 检查指针是否对齐
#define IS_ALIGNED(ptr, alignment) \
    (((uintptr_t)(ptr) % (alignment)) == 0)

void safe_access(void* data) {
    uint32_t* ptr = (uint32_t*)data;
    
    if (!IS_ALIGNED(ptr, 4)) {
        // 非对齐，使用安全方法
        uint32_t value;
        memcpy(&value, ptr, sizeof(uint32_t));
        return value;
    } else {
        // 对齐，直接访问
        return *ptr;
    }
}
3. 安全访问模式
模式A：使用memcpy（最通用）
c
// 安全地从可能非对齐的位置读取32位值
inline uint32_t read_u32_unaligned(const void* addr) {
    uint32_t value;
    memcpy(&value, addr, sizeof(uint32_t));
    return value;
}

// 安全地写入
inline void write_u32_unaligned(void* addr, uint32_t value) {
    memcpy(addr, &value, sizeof(uint32_t));
}

// 使用示例
#pragma pack(1)
struct NetworkPacket {
    uint8_t type;
    uint32_t payload;  // 非对齐
};
#pragma pack()

void process_packet(struct NetworkPacket* pkt) {
    // 安全读取非对齐的32位值
    uint32_t payload = read_u32_unaligned(&pkt->payload);

* 在32bit单片机里用32bit及其以下变量 是原子性？
#+begin_example
这是一个非常好的问题，答案并不是简单的“是”或“否”。它取决于多个关键因素。

核心结论： 在32位单片机中，对于对齐在自然边界上的32位及以下的变量，其单次读或写操作通常是原子的，但这不是绝对的保证。多核/多主系统、编译器优化、内存访问顺序等问题会打破这种原子性。

下面我们来详细分解：

1. 架构与总线的基础支持（必要条件）
对于大多数32位MCU（如基于ARM Cortex-M, RISC-V, ESP32等），其数据总线通常是32位宽的。这意味着：

对于 int32_t、uint32_t （通常4字节对齐）：一次总线事务就可以完成读取或写入。从硬件角度看，这个操作是“不可分割”的。

对于 int16_t、uint16_t （通常2字节对齐）：一次总线事务就可以完成，也是原子的。

对于 int8_t、uint8_t （1字节对齐）：一次总线事务就可以完成，也是原子的。

对于 bool （通常是1字节）：同上。

关键前提：变量必须“自然对齐”。即一个4字节变量地址是4的倍数，2字节变量地址是2的倍数。现代编译器默认会保证这一点，除非使用 packed 等特殊指令。

2. 什么情况下原子性会被破坏？（重要！）
即使硬件支持单次访问的原子性，在以下场景中，对变量的访问整体上可能不是原子的，从而引发数据竞争问题。

多步骤操作（读-改-写）：
这是最常见的误区。原子访问 ≠ 原子操作。

c
counter++; // 这不是原子的！
// 等效于： tmp = counter; tmp = tmp + 1; counter = tmp;
counter += 5; // 不是原子的
flag |= 0x80; // 不是原子的
即使 counter 是32位对齐的，上述操作在汇编层面也是多条指令，可能被中断打断，导致数据错误。

编译器优化：
编译器为了性能，可能会将变量加载到寄存器中进行一系列操作，然后再写回。在单线程下安全，但在多线程（或主程序与中断）共享变量时，会导致一个上下文看到“过时”的数据。

c
// 假设 shared_value 在中断中被修改
while (shared_value == 0) {
    // 编译器可能优化为：将 shared_value 读入寄存器R0
    // 然后一直判断 R0 == 0，导致死循环，因为看不到内存中 shared_value 的真实变化
}
需要使用 volatile 关键字来阻止这种优化，强制每次从内存读取。

多核或多主系统：
如果你的32位MCU是多核的（如ESP32双核），或者有DMA等其它总线主机可以访问内存，那么即使单次读写是原子的，也需要内存屏障来保证访问顺序和缓存一致性。一个核心的写操作可能不会立即被另一个核心看到。

非对齐访问：
如果32位变量存储在地址为 0x1003 的位置（不是4的倍数），那么CPU可能需要两次内存访问才能完成读写，这显然不是原子的。在ARM Cortex-M中，非对齐访问可能导致硬件异常或性能下降。

3. 如何确保安全的并发访问？（实践指南）
对于在中断服务程序（ISR）和主循环之间，或多个任务之间共享的变量，必须采取保护措施。

组合拳：volatile + 原子操作/关中断/互斥锁

使用 volatile：
告诉编译器此变量可能被意外改变，禁止相关优化，确保每次访问都从内存进行。

c
volatile uint32_t shared_counter;
针对读-改-写操作，选择以下一种同步机制：

关中断（对于ISR与主循环共享）：

c
// 在非中断上下文中修改共享变量
uint32_t primask = __disable_irqs(); // 平台相关指令
shared_counter++;
__restore_irqs(primask);
使用编译器提供的原子内置函数（最推荐）：

c
// GCC/Clang 等编译器
__atomic_add_fetch(&shared_counter, 1, __ATOMIC_RELAXED);
// 或者CMSIS（针对Cortex-M）提供的函数
__atomic_fetch_add(&shared_counter, 1);
这些函数会生成确保原子性的特殊指令（如LDREX/STREX）。

使用互斥锁（对于RTOS多任务）：

c
xSemaphoreTake(mutex, portMAX_DELAY);
shared_variable++;
xSemaphoreGive(mutex);
对于简单的标志位（bool）传递：

* 优先级反转
#+begin_example
设三任务优先级：A（高）> B（中）> C（低）。有一个互斥锁 mutex。假设抢占式调度、没有优先级继承。
初始（t0）
C 运行，并 获得 mutex（C = mutex 所有者）。且假设以下所有事件发生时，c还未释放该互斥量
A、B 此时都不占 CPU（可能处于就绪或未就绪，视触发时机而定）。
t1：A 变为就绪并尝试 take(mutex)
A 发现 mutex 被 C 持有 → A 进入 BLOCKED（等待 mutex）（注意：A 不是就绪态）。
C 仍然持有 mutex，但此时调度器不会让 A 运行（因为 A 阻塞了）。
t2：调度器选择下一个最高优先级的 就绪 任务 —— 这时 B 是就绪的（或被触发），B 开始运行。
因为 B 的优先级高于 C，B 抢占 C 并占用 CPU。
C 虽然持有 mutex，但此刻被抢占，无法继续执行以释放 mutex。
A 仍然阻塞在 mutex 上不能运行。
这时的事实是：A（最高）被阻塞等待 C（最低）释放 mutex，而 C 正被中优先级 B 抢占不能执行。因此高优先级任务被“间接”阻塞在中优先级任务上，发生了优先级翻转。
#+end_example
** 翻转发生的“点”（关键瞬间）
#+begin_example
翻转点 = 当中优先级任务 B 开始运行并抢占住了持有资源的低优先级任务 C，且有高优先级任务 A 正在等待该资源时。
#+end_example
** 解决思路（简短）
#+begin_example
- 优先级继承（Priority Inheritance）：当 A 阻塞在 mutex 上，系统临时把持有 mutex 的 C 提升到 A 的优先级，使 C 抢到 CPU、尽快释放 mutex，从而避免 B 抢占导致翻转。
- 优先级上限（Priority Ceiling）：在获取资源时把任务优先级直接提升到资源上限，避免中间插队。
- 以及尽量减少临界区长度、避免嵌套锁等设计手段。
#+end_example

#include <stdio.h>
#include <stdlib.h>
#include <math.h>

void gauss_solve(int n, double A[], double x[], double b[]) {
    int i, j, k, r;
    double max, tmp;

    for (k = 0; k < n - 1; k++) {
        max = fabs(A[k * n + k]);
        r = k;
        for (i = k + 1; i < n; i++) { // 修复：原本是 i < n - 1
            if (fabs(A[i * n + k]) > max) {
                max = fabs(A[i * n + k]);
                r = i;
            }
        }

        if (r != k) {
            for (i = 0; i < n; i++) {
                tmp = A[k * n + i];
                A[k * n + i] = A[r * n + i];
                A[r * n + i] = tmp;
            }
            tmp = b[k];
            b[k] = b[r];
            b[r] = tmp;
        }

        for (i = k + 1; i < n; i++) {
            double factor = A[i * n + k] / A[k * n + k];
            for (j = k; j < n; j++)
                A[i * n + j] -= factor * A[k * n + j];
            b[i] -= factor * b[k];
        }
    }

    // 回代
    for (i = n - 1; i >= 0; i--) {
        x[i] = b[i];
        for (j = i + 1; j < n; j++)
            x[i] -= A[i * n + j] * x[j];
        x[i] /= A[i * n + i];
    }
}

✅ 关键结论再确认：

    float（4 字节）最多能表示约 6～7 位有效数字，小数部分通常可精确表示约 6 位小数。

这个说法在多数情况下是 准确的，但需要理解"有效数字"和"小数位"的区别：
🔍 一、什么是有效数字（significant digits）？

有效数字指的是一个数中从第一个非零数字开始，到最后一个确定的数字为止，无论小数点在哪里。
示例：

    123.456 有 6 位有效数字

    0.000123456 也有 6 位有效数字

    12345600.0 中的有效数字是前 7 位（如果末尾是确定的）

🔍 二、float 精度的核心限制

根据 IEEE 754 单精度规范（32 位）：

    有效数字： 23 位尾数 + 隐含 1 位，约等于 6～7 位十进制有效数字

    这不是“小数点后固定几位”，而是“总共能精确表示多少位”

❗ 常见误区

    ❌ “float 可以表示 6 位小数” —— 这是不准确的泛化。

实际情况是：

    如果整数部分很大，小数部分就不精确了。

    如果整数部分很小，小数点后可以表示得更多（仍受有效数字限制）。

✅ 举个例子：

#include <stdio.h>

int main() {
    float a = 123456.7890123f;
    printf("%.10f\n", a);  // 输出：123456.7890625000（误差开始出现）
    return 0;
}

虽然你试图保留 6 位小数，但因为整数部分已经占了 6 位有效数字，小数部分只能保留 1 位左右。

再试一个小整数：

float b = 0.1234567f;
printf("%.10f\n", b);  // 输出：0.12345670（很精确）

小数部分能完整保留。
✅ 最终总结
项	float（4 字节）
总有效数字	大约 6~7 位十进制有效数字
小数位最大精度	最多可表示 6~7 位小数，但依赖于整数部分大小
精确场景建议	对精度要求高的，用 double 或使用整数 + 缩放

double d = 0;      // 合法
double e = 0.0;    // 推荐方式

建议：

    如果变量是 float 类型，建议使用 0.0f，避免从 double 到 float 的隐式转换；

    如果变量是 double 类型，则使用 0.0 即可。

说明：

虽然 0、0.0、0.0f 在语义上都等于 0，但类型不同会影响编译器的行为和警告级别，特别是在开启严格类型检查时。

需要初始化一个浮点数组为 0，也可以使用：

float arr[10] = {0};  // 所有元素都初始化为 0.0f

如有具体场景（比如内存对齐、嵌入式寄存器映射等），可以详细说明以便给出更合适的建议。
#+end_example

* opaque pointer
** opaque pointer（不透明指针）是一种 C 语言封装手法。 核心思想：

.h 里只暴露 “指针类型”
结构体内容隐藏在 .c
外部只能通过 API 操作对象
外部无法直接访问成员

典型用于：

模块封装
驱动抽象
防止全局结构体乱改
面向对象风格 C 代码

** 示例：
*** 头文件
#+begin_src c
/* motor.h */

#ifndef MOTOR_H
#define MOTOR_H

typedef struct motor motor_t;

motor_t *motor_create(void);
void motor_set_speed(motor_t *m, int speed);
int motor_get_speed(motor_t *m);
void motor_destroy(motor_t *m);

#endif
#+end_src

#+begin_example
这里：
typedef struct motor motor_t; 只是声明了： struct motor; 外部不知道成员。
#+end_example
*** 真正定义在 .c：

#+begin_src c
/* motor.c */

#include "motor.h"
#include <stdlib.h>

struct motor
{
    int speed;
    int current;
    int state;
};

motor_t *motor_create(void)
{
    motor_t *m = malloc(sizeof(motor_t));

    if (m)
    {
        m->speed = 0;
        m->current = 0;
        m->state = 0;
    }

    return m;
}

void motor_set_speed(motor_t *m, int speed)
{
    m->speed = speed;
}

int motor_get_speed(motor_t *m)
{
    return m->speed;
}

void motor_destroy(motor_t *m)
{
    free(m);
}
#+end_src

*** 外部代码：

#+begin_src  c
#include "motor.h"

int main(void)
{
    motor_t *m = motor_create();

    motor_set_speed(m, 100);

    int speed = motor_get_speed(m);

    motor_destroy(m);
}
#+end_src

#+begin_src c

因为外部根本不知道结构体内容。
#+end_src

*** 优点：

- 真正的数据保护,比： extern struct xxx g_xxx; 强很多。 降低耦合

- 结构体成员改了：
#+begin_src c

{
    float speed;

外部无需重新修改代码。
#+end_src

- 驱动状态
- 通信协议栈
- GUI对象

#+begin_src C
          #define BITCOUNT(x)  (((BX_(x)+(BX_(x)>>4)) & 0x0F0F0F0F) % 255)
          #define  BX_(x)      ((x) - (((x)>>1)&0x77777777)            \
                        - (((x)>>2)&0x33333333)            \
                        - (((x)>>3)&0x11111111))

      -- really weird C code to count the number of bits in a word
#+end_src
#+begin_example
这段代码是一个经典的 位计数（population count，popcount） 算法，用于统计一个整数中有多少个 1。

例如：

x = 0b10110100

共有 4 个 1

它的时间复杂度是 O(1)，不需要循环。

整体结构
#define BX_(x) \
    ((x) - (((x)>>1)&0x77777777) \
         - (((x)>>2)&0x33333333) \
         - (((x)>>3)&0x11111111))

#define BITCOUNT(x) \
    (((BX_(x)+(BX_(x)>>4)) & 0x0F0F0F0F) % 255)

实际上分两步：

BX_(x)：把每个 nibble（4 bit）变成该 nibble 中 1 的个数。
BITCOUNT(x)：把所有 nibble 的计数累加起来。
第一步：为什么这样减？

假设一个 nibble：

abcd

它表示

a*8+b*4+c*2+d

其中

a,b,c,d ∈ {0,1}

算法计算

x
- ((x>>1)&0x77777777)
- ((x>>2)&0x33333333)
- ((x>>3)&0x11111111)

实际上就是

8a+4b+2c+d
-(4a+2b+c)
-(2a+b)
-a

整理：

=(8-4-2-1)a
 +(4-2-1)b
 +(2-1)c
 +d

=a+b+c+d

也就是说：

每个 nibble 最终变成了该 nibble 中 1 的数量。

这是这个算法最巧妙的地方。

例如

1101

有三个 1。

经过上述计算：

1101 (13)
0110
0011
0001

13-6-3-1=3

得到

0011

就是数字 3。

第二步

得到

BX_(x)

之后，

每个 nibble 都已经是

0~4

例如

0001 0010 0011 0000

表示

1
2
3
0

然后

BX_(x)+(BX_(x)>>4)

就是把相邻 nibble 加起来。

再

&0x0F0F0F0F

去掉进位。

于是每个 byte 都变成

低 nibble + 高 nibble

即

每个 byte 中 1 的数量

范围

0~8
为什么 %255

此时四个 byte 分别是

b3 b2 b1 b0

每个都是

0~8

组成

b3<<24
+b2<<16
+b1<<8
+b0

而

256 ≡ 1 (mod 255)

因此

b3*256³
+b2*256²
+b1*256
+b0

≡ b3+b2+b1+b0 (mod255)

于是

%255

就把四个 byte 的值全部相加了。

这正是整个 32 位整数中 1 的总数。

由于 32 位整数最多只有 32 个 1，结果不会超过 32，因此不会与 255 取模产生歧义。

举个例子

假设

x = 0xF0F0000F

四个字节分别有

11110000 -> 4
11110000 -> 4
00000000 -> 0
00001111 -> 4

经过 BX_ 后：

04040004

再经过

+(>>4)
&

得到

04040004

（每个 byte 已经表示该字节中的 1 的数量。）

最后

4+4+0+4=12

所以

BITCOUNT(x)=12
与现代编译器相比

这段代码来自早期的位运算技巧（又称 bit twiddling hacks），在没有硬件支持和编译器内建函数时非常有价值。

现代编译器通常提供更高效的方法，例如：

__builtin_popcount(x)      // GCC、Clang
__builtin_popcountl(x)
__builtin_popcountll(x)

在支持 POPCNT 指令的处理器上，这些内建函数通常会直接生成一条硬件指令，速度通常比这种宏更快，也更易读。对于嵌入式平台，如果处理器没有专门的位计数指令，这类无循环的算法仍然具有参考价值。
#+end_example
* uint类型跟负数比较
#+begin_example
在 C 语言里，uint32_t 和负数比较时要特别注意：负数很可能会被转换成无符号数，结果和直觉完全不同。
例如：
uint32_t var = 10;
if (var < -5) {
    // ...
}
这里不是简单地比较：
10 < -5
而是发生了整数转换。
-5 会转换成 uint32_t：
-5 → 0xFFFFFFFB → 4294967291
所以实际比较相当于：
if (10 < 4294967291U)
结果是：
true
这就是常见的坑。
#+end_example
