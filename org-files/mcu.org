** 依赖方向严格保持：
App
 ↓
Service
 ↓
Driver
 ↓
BSP / MCU

** 可以把四层用一句话记住
BSP      = 板子有什么
Driver   = 硬件怎么用
Service = 系统提供什么能力
App      = 产品要做什么

** 例如：
“用户修改电机最大电流”
        ↓
Control App
        ↓
Parameter Service
        ↓
Storage Service
        ↓
LittleFS
        ↓
Flash Driver

** 不是所有 Task 都属于 App
** App 最核心的东西：状态机
*** 对于 MCU，App 很多时候不是传统 Linux 那种“启动一个 main 然后执行到底”，而是：

INIT
  ↓
IDLE
  ↓
READY
  ↓
RUNNING
  ↓
STOPPING
  ↓
FAULT

*** 例如：
#+begin_src C
typedef enum {
    APP_INIT,
    APP_IDLE,
    APP_RUN,
    APP_FAULT,
} app_state_t;
#+end_src

*** 然后：
#+begin_src C
void control_app_task(void *arg)
{
    app_state_t state = APP_INIT;

    for (;;) {

        switch (state) {

        case APP_INIT:
            parameter_service_load();
            state = APP_IDLE;
            break;

        case APP_IDLE:
            if (start_request)
                state = APP_RUN;
            break;

        case APP_RUN:
            motor_service_run();
            if (fault)
                state = APP_FAULT;
            break;

        case APP_FAULT:
            motor_service_stop();
            break;
        }

        tx_thread_sleep(10);
    }
}
#+end_src
这就是一个非常典型的 MCU Application 层。

** App 层最好理解成“产品功能编排层”,建议 App 采用比较薄的结构
* app怎么划分和抽象提取

可以把这个问题拆成两个动作：

怎么划分 App
怎么从具体项目中提取出 App 层，而不是把 Service 又套一层

核心原则是：

按“业务职责/业务生命周期”划分 App，而不是按硬件、外设或函数数量划分。

** 1. 先看一个具体项目

假设 STM32 是一个电机控制设备：

硬件：
电机
编码器
ADC
按键
RS485
Flash
温度传感器

不要直接划成：

ADC App
PWM App
UART App
Flash App
Encoder App

这些基本都是 Driver/Service 的职责。

更合理的是：

App
├── MotorApp
├── CommunicationApp
├── ParameterApp
├── AlarmApp
└── SystemApp

因为这些才是业务概念。

例如：

MotorApp
    “设备怎么启动、运行、停止、故障”

CommunicationApp
    “设备怎么和上位机通信、处理命令”

ParameterApp
    “设备参数怎么加载、修改、保存”

AlarmApp
    “什么情况下报警、报警怎么恢复”

SystemApp
    “设备启动、初始化、运行模式、关机”
** 2. 一个非常实用的判断方法

问自己：

如果换一套硬件，这部分代码还成立吗？

例如：

LL_TIM_EnableCounter(TIM1);

显然不是 App。

motor_set_pwm(500);

可能属于 Motor Service。

#+begin_exampleC
if (target_speed > 0 && motor_state == IDLE)
   motor_start();
#+end_example

这就是 App 业务逻辑。

所以可以形成一个判断链：

是不是直接操作硬件？
        │
       是
        ↓
     Driver

不是
        │
        ↓
是不是一个可以被多个业务复用的能力？
        │
       是
        ↓
    Service

不是
        │
        ↓
是不是产品自己的业务规则？
        │
       是
        ↓
       App
** 3. App 怎么“抽象提取”

这里最重要。

不要一开始就设计：

#+begin_src C
struct xxx_app_ops {
    ...
};
#+end_src

然后强行抽象。

更好的方法是：

先写一个具体 App，再从业务逻辑中提取稳定的边界。

例如最开始你可能写成：

#+begin_src C
void motor_task(void)
{
    motor_init();

    while (1) {

        if (start_button_pressed()) {

            motor_start();

            while (!speed_reached()) {
                ...
            }

            motor_set_speed(1000);
        }

        if (over_current()) {
            motor_stop();
        }

        tx_thread_sleep(10);
    }
}
#+end_src

这时候业务、Task、硬件调用全部混在一起。

先拆：

MotorTask
    ↓
MotorApp
    ↓
MotorService

变成：

#+begin_src C
void motor_task(void *arg)
{
    while (1) {
        motor_app_process();
        tx_thread_sleep(10);
    }
}
#+end_src

然后：

#+begin_src C
void motor_app_process(void)
{
    switch (app.state) {

    case MOTOR_IDLE:
        if (app.start_request) {
            app.state = MOTOR_STARTING;
        }
        break;

    case MOTOR_STARTING:
        if (motor_service_speed_ready()) {
            app.state = MOTOR_RUNNING;
        }
        break;

    case MOTOR_RUNNING:
        if (motor_service_over_current()) {
            app.state = MOTOR_FAULT;
        }
        break;

    case MOTOR_FAULT:
        motor_service_stop();
        break;
    }
}
#+end_src

这时候 App 已经出现了。

** 4. App 的真正抽象通常是“事件 → 状态 → 动作”

所以我更推荐把 App 看成：

             Event
               │
               ▼
        ┌──────────────┐
        │   App FSM    │
        │              │
        │   State      │
        │      +       │
        │   Event      │
        │      ↓       │
        │   Action     │
        └──────┬───────┘
               │
               ▼
           Service

例如：

Event:

START
STOP
FAULT
TIMEOUT
COMM_CMD
PARAM_CHANGED

状态：

INIT
IDLE
STARTING
RUNNING
STOPPING
FAULT

动作：

motor_service_start()
motor_service_stop()
alarm_service_raise()
parameter_service_save()

于是 App 本质上变成：

state + event -> state + action

这就是非常稳定的抽象。

** 5. 不要把 Service 的 API 直接变成 App API

这是很容易犯的错误。

比如 Service：

motor_service_start();
motor_service_stop();
motor_service_set_speed();
motor_service_get_speed();

然后 App 又写：

motor_app_start();
motor_app_stop();
motor_app_set_speed();
motor_app_get_speed();

如果只是这样：

App
 ↓
Service
 ↓
Driver

那么这个 App 基本没有价值。

因为它只是：

motor_app_start()
    ↓
motor_service_start()

这就是你之前问的“Interface 层跟直接调用没区别”的同类问题。

真正有价值的 App 应该加入业务语义。

例如：

motor_app_start_production();

内部：

检查参数
检查安全条件
检查故障
确认设备状态
↓
启动电机
↓
等待速度建立
↓
进入 RUNNING

这时候：

Service = 怎么控制电机

App = 什么情况下允许电机运行

这就是边界。

** 6. 如何判断两个功能应该属于一个 App

可以用一个很实用的标准：

如果它们共享状态机 → 一个 App

例如：

启动
运行
停止
故障
恢复

这些天然属于：

MotorApp
如果它们只是共享底层能力 → 不一定一个 App

例如：

MotorApp ──┐
           ├── ParameterService
AlarmApp ──┤
           └── LogService
SystemApp ─┘

它们使用同一个 Service，但业务上是不同 App。

如果两个功能之间需要大量互相调用

例如：

MotorApp → CommunicationApp
CommunicationApp → MotorApp
MotorApp → CommunicationApp

出现大量这种关系：

A ↔ B

通常说明划分有问题。

更可能应该是：

             System/App Controller
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
      MotorApp   CommApp   AlarmApp

或者提取一个共享 Service。

** 7. App 不一定需要接口

这一点也很重要。

Service 通常比较值得做接口：

#+begin_src C
struct storage_ops {
    int (*read)(...);
    int (*write)(...);
};
#+end_src

因为你可能替换：

Internal Flash
     ↓
SPI Flash
     ↓
EEPROM

但 App 通常不需要这种：

#+begin_src C
struct motor_app_ops {
    ...
};
#+end_src

因为 App 是产品业务实现。

例如：

project_A/
    app/
        motor_app.c
        system_app.c

project_B/
    app/
        pump_app.c
        system_app.c

你真正希望复用的是：

Service
Driver
BSP

而不是强行让：

MotorApp

成为一个通用库。

** 8. 那么什么东西值得从 App 提取出去？

当你发现 App 里面出现这种代码：

参数管理
日志
通信协议
定时器
文件系统
设备状态
报警

而这些东西本身可以被多个 App 使用时，就开始提取。

例如：

原来的 MotorApp

MotorApp
├── 参数读取
├── Flash 操作
├── 日志
├── 电机控制
├── 报警
└── Modbus

逐渐变成：

App
└── MotorApp
      │
      ├── ParameterService
      ├── LogService
      ├── AlarmService
      ├── MotorService
      └── ModbusService

最终 MotorApp 只剩：

业务规则
状态机
业务数据
业务事件

这就是“抽象提取”。

** 9. 最终我建议你把 App 目录做得非常简单

例如：

app/
├── system/
│   ├── system_app.c
│   └── system_app.h
│
├── motor/
│   ├── motor_app.c
│   ├── motor_app.h
│   └── motor_state.h
│
├── communication/
│   ├── communication_app.c
│   └── communication_app.h
│
└── parameter/
    ├── parameter_app.c
    └── parameter_app.h

其中：

#+begin_src C
typedef struct {
    motor_state_t state;

    uint32_t target_speed;
    uint32_t actual_speed;

    bool start_request;
    bool stop_request;

} motor_app_t;
#+end_src

然后：
void motor_app_init(void);
void motor_app_process(void);
void motor_app_event(motor_event_t event);

这已经足够。

Task：

#+begin_src C
void motor_task(void *arg)
{
    for (;;) {
        motor_app_process();
        tx_thread_sleep(10);
    }
}
#+end_src

App：

motor_app_process()
    ↓
状态机
    ↓
MotorService
AlarmService
ParameterService

所以整个设计的关键不是“怎么把 App 抽象得很漂亮”，而是：

让 App 成为业务规则的边界。

当一段代码回答的是“这个产品应该怎么工作”，放 App。

当回答的是“这个能力怎么提供”，放 Service。

当回答的是“这个芯片/外设怎么操作”，放 Driver。

这三个边界一旦稳定，App 的划分通常会自然出现。

#+begin_example
b 16，在当前低16行代码出加断点。
b i=1，当i等于1时停止，类似于这种条件式断点的方式也是GDB独有的一种强大功能。

**** s，step缩写，会进入子函数的单步运行
**** n，next缩写，即会跳过子函数的单步运行
**** si，单指令执行，碰到子程序调用指令则进入子程序。
**** ni，单行汇编执行，碰到子程序调用指令就执行完子程序。汇编指令级别的单步调试不仅用来调汇编，而且可以用来观察哪一步触发了fault，甚至可以发现编译器深层次的bug。
**** finish，子程序执行到返回。
**** u，until缩写使用时后方加行号如： u 16 即运行到第16行 finish，完成并跳出当前的子函数
**** p，print缩写，使用时后面加变量名称如：p tmp ，用来显示变量数值
**** display ，使用时后面加变量名称如：display tmp ，用于跟踪变量数值，在每次执行停下时会自动显示变量数值。
**** bt，查看函数调用链
**** x，查看内存区域的值，语法是x /FMT 地址。FMT处要填三个东西：个数、输出格式、长度:输出格式可以有二进制、八进制、十进制等等，长度有单字节、双字节、四字节等等。比方说：x /1xw 0x40023830，表示查看0x40023830处一个四字节整数，以十六进制输出。
**** q/Ctrl+d，使用q即quit指令或快捷键Ctrl+d来正常退出GDB

*** GDB打断点
| b *0x08001234 | 在指定地址下断点                              |
| b 16          | 在当前源文件第 16 行下断点                    |
| b .           | 在当前执行位置（当前 PC 对应的代码行）下断点 |
| break *$pc    | 直接在当前 PC 指向的指令地址设置断点。       |
| b main.c:42   | 例如当前停在 main.c:42：                      |
