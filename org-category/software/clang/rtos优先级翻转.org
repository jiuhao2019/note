* 优先级反转
#+begin_example
设三任务优先级：A（高）> B（中）> C（低）。有一个互斥锁 mutex。假设抢占式调度、没有优先级继承。
初始（t0）
C 运行，并 获得 mutex（C = mutex 所有者）。且假设以下所有事件发生时，c还未释放该互斥量
A、B 此时都不占 CPU（可能处于就绪或未就绪，视触发时机而定）。
t1：A 变为就绪并尝试 take(mutex)
A 发现 mutex 被 C 持有 → A 进入 BLOCKED（等待 mutex）（注意：A 不是就绪态）。
C 仍然持有 mutex，但此时调度器不会让 A 运行（因为 A 阻塞了）。
t2：调度器选择下一个最高优先级的 就绪 任务 —— 这时 B 是就绪的（或被触发），B 开始运行。
因为 B 的优先级高于 C，B 抢占 C 并占用 CPU。
C 虽然持有 mutex，但此刻被抢占，无法继续执行以释放 mutex。
A 仍然阻塞在 mutex 上不能运行。
这时的事实是：A（最高）被阻塞等待 C（最低）释放 mutex，而 C 正被中优先级 B 抢占不能执行。因此高优先级任务被“间接”阻塞在中优先级任务上，发生了优先级翻转。
#+end_example
** 翻转发生的“点”（关键瞬间）
#+begin_example
翻转点 = 当中优先级任务 B 开始运行并抢占住了持有资源的低优先级任务 C，且有高优先级任务 A 正在等待该资源时。
#+end_example
** 解决思路（简短）
#+begin_example
- 优先级继承（Priority Inheritance）：当 A 阻塞在 mutex 上，系统临时把持有 mutex 的 C 提升到 A 的优先级，使 C 抢到 CPU、尽快释放 mutex，从而避免 B 抢占导致翻转。
- 优先级上限（Priority Ceiling）：在获取资源时把任务优先级直接提升到资源上限，避免中间插队。
- 以及尽量减少临界区长度、避免嵌套锁等设计手段。
#+end_example
