* 在32bit单片机里用32bit及其以下变量 是原子性？
#+begin_example
这是一个非常好的问题，答案并不是简单的“是”或“否”。它取决于多个关键因素。

核心结论： 在32位单片机中，对于对齐在自然边界上的32位及以下的变量，其单次读或写操作通常是原子的，但这不是绝对的保证。多核/多主系统、编译器优化、内存访问顺序等问题会打破这种原子性。

下面我们来详细分解：

1. 架构与总线的基础支持（必要条件）
对于大多数32位MCU（如基于ARM Cortex-M, RISC-V, ESP32等），其数据总线通常是32位宽的。这意味着：

对于 int32_t、uint32_t （通常4字节对齐）：一次总线事务就可以完成读取或写入。从硬件角度看，这个操作是“不可分割”的。

对于 int16_t、uint16_t （通常2字节对齐）：一次总线事务就可以完成，也是原子的。

对于 int8_t、uint8_t （1字节对齐）：一次总线事务就可以完成，也是原子的。

对于 bool （通常是1字节）：同上。

关键前提：变量必须“自然对齐”。即一个4字节变量地址是4的倍数，2字节变量地址是2的倍数。现代编译器默认会保证这一点，除非使用 packed 等特殊指令。

2. 什么情况下原子性会被破坏？（重要！）
即使硬件支持单次访问的原子性，在以下场景中，对变量的访问整体上可能不是原子的，从而引发数据竞争问题。

多步骤操作（读-改-写）：
这是最常见的误区。原子访问 ≠ 原子操作。

c
counter++; // 这不是原子的！
// 等效于： tmp = counter; tmp = tmp + 1; counter = tmp;
counter += 5; // 不是原子的
flag |= 0x80; // 不是原子的
即使 counter 是32位对齐的，上述操作在汇编层面也是多条指令，可能被中断打断，导致数据错误。

编译器优化：
编译器为了性能，可能会将变量加载到寄存器中进行一系列操作，然后再写回。在单线程下安全，但在多线程（或主程序与中断）共享变量时，会导致一个上下文看到“过时”的数据。

c
// 假设 shared_value 在中断中被修改
while (shared_value == 0) {
    // 编译器可能优化为：将 shared_value 读入寄存器R0
    // 然后一直判断 R0 == 0，导致死循环，因为看不到内存中 shared_value 的真实变化
}
需要使用 volatile 关键字来阻止这种优化，强制每次从内存读取。

多核或多主系统：
如果你的32位MCU是多核的（如ESP32双核），或者有DMA等其它总线主机可以访问内存，那么即使单次读写是原子的，也需要内存屏障来保证访问顺序和缓存一致性。一个核心的写操作可能不会立即被另一个核心看到。

非对齐访问：
如果32位变量存储在地址为 0x1003 的位置（不是4的倍数），那么CPU可能需要两次内存访问才能完成读写，这显然不是原子的。在ARM Cortex-M中，非对齐访问可能导致硬件异常或性能下降。

3. 如何确保安全的并发访问？（实践指南）
对于在中断服务程序（ISR）和主循环之间，或多个任务之间共享的变量，必须采取保护措施。

组合拳：volatile + 原子操作/关中断/互斥锁

使用 volatile：
告诉编译器此变量可能被意外改变，禁止相关优化，确保每次访问都从内存进行。

c
volatile uint32_t shared_counter;
针对读-改-写操作，选择以下一种同步机制：

关中断（对于ISR与主循环共享）：

c
// 在非中断上下文中修改共享变量
uint32_t primask = __disable_irqs(); // 平台相关指令
shared_counter++;
__restore_irqs(primask);
使用编译器提供的原子内置函数（最推荐）：

c
// GCC/Clang 等编译器
__atomic_add_fetch(&shared_counter, 1, __ATOMIC_RELAXED);
// 或者CMSIS（针对Cortex-M）提供的函数
__atomic_fetch_add(&shared_counter, 1);
这些函数会生成确保原子性的特殊指令（如LDREX/STREX）。

使用互斥锁（对于RTOS多任务）：

c
xSemaphoreTake(mutex, portMAX_DELAY);
shared_variable++;
xSemaphoreGive(mutex);
对于简单的标志位（bool）传递：
如果只是简单地从ISR设置一个标志，在主循环中读取并清除，利用硬件单次读写的原子性，并加上 volatile，通常是安全的。但为了确保读写顺序，有时也需要简单的内存屏障。

c
volatile bool data_ready = false;
// ISR中
data_buffer = new_data;
__DSB(); // 数据同步屏障，确保写完成
data_ready = true;
// 主循环中
if (data_ready) {
    __DSB(); // 确保读到最新的 data_ready
    process(data_buffer);
    data_ready = false;
}
总结
变量类型（自然对齐）	单次读或写（如 a = b）	读-改-写操作（如 a++）	注意事项
8位（uint8_t）	通常是原子的	不是原子的	需volatile防优化
16位（uint16_t）	通常是原子的	不是原子的	需volatile防优化
32位（uint32_t）	通常是原子的	不是原子的	需volatile防优化；多核需屏障
最佳实践：
不要依赖“通常的原子性”。对于任何在并发环境中（ISR/主循环、多任务、多核）共享的变量，总是：

声明为 volatile。

使用原子操作函数或明确的同步机制（关中断、锁）来进行任何非单一读/写的操作。

这样可以写出健壮、可移植且安全的嵌入式代码。
